# 协作说明（GitHub + 飞书）

这份文档给组员看。照着做就行，不需要你懂 git 原理。

---

## 一、分工：谁管什么

| 角色 | 谁 | 干什么 |
|---|---|---|
| 主线（owner） | 建仓库的人 | 审核 PR、合并到 `main`、发版 |
| 支线（contributor） | 其他组员 | 在自己的分支上做功能，提 PR 等合并 |

**代码只放在 GitHub，飞书只用来沟通和记任务。** 飞书不能托管代码，也不能开分支；每次用飞书发 zip 传代码，最后合并都得靠人眼比对，是这类作业最容易翻车的地方。

---

## 二、第一次拿到代码（每个人只做一次）

先装好 Python 3.10+（勾选 Add Python to PATH）和 Git，然后在想放项目的文件夹里打开命令行：

```bash
git clone https://github.com/<仓库地址>/secondhand.git
cd secondhand
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
python app.py
```

浏览器打开 http://127.0.0.1:5000 能看到登录页，说明环境好了。
`venv` 和 `market.db` 不会从仓库同步，自己本地生成，这是正常的。

## 三、三条铁律

**1. 永远不在 `main` 上写代码。**
`main` 只接受合并。你在 `main` 上改完再推，会被 GitHub 拒掉（分支保护），白干。

**2. 动手前先拉最新代码。**
```bash
git checkout main
git pull
```
在三天前的代码上开发，合并时必冲突。

**3. 一个文件同一时间只由一个人改。**
`static/index.html`、`static/app.js`、`static/style.css` 这三个文件是撞车高发区。
**按页面/模块分人，不要按功能分人**——一个功能常常横跨前后端，会牵扯所有人。

建议这样切：

| 模块 | 主要改哪些文件 | 建议负责 |
|---|---|---|
| 后端接口与业务规则 | `app.py` | A |
| 数据表与测试数据 | `models.py`、`seed.py` | A（改表结构要提前说） |
| 首页 / 搜索 / 筛选 | `index.html` 首页段 + `app.js` 首页段 | B |
| 消息 / 改价 | `index.html` 消息段 + `app.js` 消息段 | C |
| 我的商品 / 订单 | `index.html` 对应段 + `app.js` 对应段 | D |
| 样式与配色 | `style.css` | 一个人统一改，别人不要动 |

每个人改 `index.html` 只改自己那一段，别顺手重排整个文件——重排会让 diff 变成几千行，合并等于手工重写。

## 四、做一个功能（每次都是这五步）

```bash
# 1. 更新主线
git checkout main
git pull

# 2. 开自己的分支，名字写清楚干什么
git checkout -b feature/首页搜索栏

# 3. 改代码，本地跑通再说
python app.py

# 4. 提交
git add .
git commit -m "首页：加搜索栏，支持按商品名检索"

# 5. 推到 GitHub
git push -u origin feature/首页搜索栏
```

推完 GitHub 页面上会出现一个黄色的 **Compare & pull request** 按钮，点它 → 写一句这个 PR 做了什么 → **Create pull request**。

然后去飞书群里把 PR 链接贴一下，@ 主线负责人。

---

## 五、合并（主线负责人做）

1. 打开 PR 页面，点 **Files changed** 看一遍改了什么，有没有把 `venv/`、`market.db` 提交上来
2. **本地跑一遍再合**，不要只看 diff：
```bash
git checkout feature/首页搜索栏
python app.py
```
3. 没问题就点 **Merge pull request** → Confirm merge
4. 合完在自己的 `main` 上拉一次：
```bash
git checkout main
git pull
```
5. 通知大家 `git pull`

## 六、冲突了怎么办

不要慌，冲突不是错误，是两个人改了同一行。

```bash
git checkout main
git pull
git checkout feature/你的分支
git merge main
```

打开提示冲突的文件，搜索 `<<<<<<<`，会看到：

```
<<<<<<< HEAD
你这边的代码
=======
main 上的代码
>>>>>>> main
```

**留下要的那份，把 `<<<<<<<`、`=======`、`>>>>>>>` 三行删掉**，然后：

```bash
git add .
git commit -m "解决冲突"
git push
```

实在搞不定，就在飞书群里说一声，别硬删文件重来——那会丢掉别人的代码。

## 七、常见报错对照

| 报错 | 原因 | 怎么解决 |
|---|---|---|
| `Authentication failed` | 用了登录密码 | 改用 Personal Access Token（GitHub → Settings → Developer settings → Tokens (classic)，勾 `repo`） |
| `Updates were rejected` | 远端有你本地没有的提交 | 先 `git pull`，再 push |
| `protected branch` | 直接往 main 推了 | 开分支，走 PR |
| `fatal: not a git repository` | 不在项目目录里 | `cd` 到 `secondhand` 目录 |
| `ModuleNotFoundError: flask` | 虚拟环境没激活 | `venv\Scripts\activate` 再跑 |
| `Port 5000 is in use` | 上次的服务没关 | 关掉旧窗口，或改 `app.py` 末尾的端口 |

## 八、飞书怎么配合

1. **建群**「二手平台开发」，所有 PR 链接、报错截图往群里发
2. **多维表格当看板**，四列足够：任务 / 分支名 / 负责的文件 / 状态（未开始、进行中、待合并、已完成）。这样谁在改哪个文件一眼可见
3. **通知机器人**（可选）：飞书群设置里加 GitHub 机器人，按提示到 GitHub 仓库 Settings → Webhooks 配置，之后有人提 PR 群里自动弹消息
4. 文档、PPT、素材放飞书云文档，**代码永远不要用飞书传**

---

## 九、给主线负责人的两个提醒

- **尽早开分支保护**：Settings → Branches → Add branch protection rule → 填 `main` → 勾 Require a pull request before merging。晚开一天，就有人往 main 里塞了坏代码
- **协作者不要用 fork 流程**：Settings → Collaborators 直接把人加进来，他们能在同一个仓库开分支。fork + PR 对初学者是纯负担
